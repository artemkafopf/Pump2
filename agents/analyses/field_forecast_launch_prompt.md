## Процедура

1. **Разведка поля.** Сколько пробегов/отказов, сколько живых насосов, какие страты
   (`h2s_class` × `contractor_group`) и сколько событий в каждой, есть ли поле в плане ПП
   и какой префикс кодов (`config.FIELD_PREFIX_MAP`). Печатай числа, не предполагай.
2. **Модели.** Резолвить каждую скважину в страту реестра `esp_models.csv`
   (`survival.StrataModel.resolve`, бандл — актуальный из `config.BUNDLE_DATE`, если для
   поля нет своего). Если у поля одна страта — можно как Mc; если несколько —
   ОБЯЗАТЕЛЬНО `vt_forecast.forecast_multi` (по стратам + сшивка).
3. **Проверка моделей против цензурированной KM** ДО прогноза: max|dS| по каждой страте.
   Если реестр не проходит (>0.05) — сообщи и предложи переподгонку, но НЕ подменяй
   молча. Переподгонка — только сетка cal/op × c0/3/7/30 × k1/k2, шипится только
   СЕРВИРУЕМЫЙ c0-фит, и только если он бьёт реестр (порог выигрыша KS 0.005).
4. **Вселенная скважин — ПЛАН, а не наши пробеги**: `live_fleet` + `plan_entrants`
   (префиксы поля!) + `plan_metadata`. Знаменатель интенсивности —
   `active_fleet_by_month(codes=ВСЯ популяция поля | entrants)`, НЕ live_codes.
5. **Прогноз и раскладка.** `repair_payload_multi` (или `repair_payload`), горизонт 18
   мес. Раскладка — штатная: plain debt + guard90, `initial_debt` НЕ передавать.
6. **История факт-vs-модель** (`history_match_multi`, поле передать явно) + O/E по годам.
   ⚠ Группировать по ПРОБЕГАМ, не по скважинам (подрядчик меняется между пробегами).
7. **Книга** через `repair_compat.write_excel` + листы «Интенсивность отказов» (с
   графиком: факт — пунктир с маркерами, модель — сплошная), «История_факт_модель»,
   «Страты», «Порядок_отказов». Слой Ql — второй книгой, только если c4_gate пройден;
   иначе пометить СЦЕНАРНЫМ.
8. **Выход** — `results_dir("production_risk_<field>_svodprognoz")`.

## Обязательные проверки перед тем, как показать результат

* `ННО <= 90 сут`: должно быть **0** строк. Если нет — guard не сработал, разбирайся.
* `O/E` истории в диапазоне ~0.9–1.1. Если нет — НЕ подгоняй, а найди причину
  (страта/часы/популяция) и доложи.
* `ρ(возраст, дата первого отказа)` по стратам: доложи ЗНАК и объясни его через `β`
  страты. Знак β>1 → старые первыми; β<1 → молодые первыми; β≈1 → порядка нет и
  очередь читать как приоритет НЕЛЬЗЯ.
* Сверить `n_failures` фита с `esp_models.csv` (стандартная ловушка популяции).
* Тесты: `cd backend && ../.venv/Scripts/python.exe -m pytest tests/ -q` — 404 passed.

## Заметки для того, кто правит сам промпт

* Эталон для копирования — **`export_vt_svodprognoz.py`**, а не Mc: он умеет несколько
  страт, а одностратное поле — частный случай. Mc-скрипт держит одну `SurvivalModel` на
  весь парк и на другое поле переносится плохо.
* `vt_forecast.py` назван по полю исторически, но по сути это **многострановая обвязка**:
  `VT_PLAN_FIELD`/`VT_PREFIXES`/`VT_TAU` — единственное, что в нём Vt-специфично.
  При третьем поле имеет смысл переименовать в `multi_forecast.py` и вынести эти три
  константы в параметры.
* Поля с тонкой историей (`Bt`, `Ki`, …) почти наверняка резолвятся в `Global_Pooled`.
  Это допустимо, но обязано быть ЯВНО помечено в листе «Страты» (колонка `источник`),
  иначе читатель решит, что модель своя.
