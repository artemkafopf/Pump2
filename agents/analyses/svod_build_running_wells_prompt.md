# Свод: добавить РАБОТАЮЩИЕ (цензурированные) пробеги — задача для сборщика Свода

Дата: **2026-07-22** (обновлено по результатам разбора ПЕРВОЙ сборки — см. §8).
Адресат — процесс, собирающий «Отказы свод с анализом.xlsx» из
ПДК / Big / телеметрии / техрежима. Документ самодостаточный.

---

## 1. Проблема в одном предложении

Исходный Свод содержал ТОЛЬКО ЗАКРЫТЫЕ пробеги (у всех есть «Дата остановки»), потому что
он строится из ПДК — а ПДК это журнал РЕМОНТОВ (событие = подъём). Первая переработанная
сборка (файл заменён 2026-07-22) открытые пробеги ДОБАВИЛА — 550 строк; §8 разбирает,
что получилось и что осталось починить.

## 2. Почему это критично для survival-анализа

Оценка выживания по одним отказам систематически ЗАНИЖАЕТ ресурс: она не видит насосы,
которые ещё не сломались. Цензурированные (работающие) пробеги обязаны участвовать в
подгонке — это половина информации. До переработки живой парк добирался из Big
(561 пробег против 12 из Свода) — источника с фантомами (рассольные стволы, устаревшие
открытые строки). **После переработки потребитель ПОЛНОСТЬЮ отказался от открытых строк
Big: Свод — единственный источник живого парка (сейчас 548 скважин). Ошибка покрытия в
Своде теперь напрямую становится ошибкой прогноза.**

## 3. Что именно добавить (выполнено в первой сборке, кроме наработки)

**Открытый (цензурированный) пробег на КАЖДЫЙ насос, работающий на дату среза:**
монтаж известен, «Дата остановки» ПУСТА, «Причина остановки» пуста, «Наработка (сут)» =
наработка на дату среза (⚠ в первой сборке НЕ заполнена — §8.2). Такой пробег в
survival-анализе — правое цензурирование в возрасте на дату среза.

## 4. Правильная обработка (источники и приоритет)

1. **Кто сейчас работает — из ТЕХРЕЖИМА** (текущий статус скважины). Насос «живой», если
   его статус на дату среза — в работе / в накоплении / в простое, но НЕ поднят.
   Техрежим — авторитетный источник ТЕКУЩЕГО состояния (на сверке он подтвердил возраст
   127 из 132 живых насосов старше 2 лет).
2. **Дата монтажа живого пробега** — из ПДК/Big: дата монтажа ПОСЛЕДНЕГО пробега без
   подъёма. Если последний пробег в ПДК ЗАКРЫТ, а техрежим говорит «в работе» — после
   него был новый монтаж; брать из Big или из даты ввода ГТМ (ДФ-04).
3. **Наработка живого пробега** = min( ННО по техрежиму, календарь `срез − монтаж` ).
   ⚠ Часы РАСХОДЯТСЯ: календарный возраст на ~49 сут (IQR 48–51) больше техрежимной ННО
   при том же срезе — причина не локализована. Писать ОДНУ определённую величину
   (рекомендуется техрежимную ННО) и помечать источник.
4. **Дату среза техрежима фиксировать В ФАЙЛЕ** (метаданные/лист/ячейка). В первой
   сборке её пришлось сообщать устно (30.06.2026) и зашивать константой у потребителя
   (`config.SVOD_OPEN_ASOF`) — при каждом новом дропе её надо не забыть поднять. Дата в
   самом файле снимает этот ручной шаг.
5. **Не выдумывать подъём.** У живого пробега «Дата остановки» и «Причина» ПУСТЫЕ — это
   признак цензуры (в первой сборке выполнено).
6. **Живой пробег не может ПЕРЕСЕКАТЬСЯ с закрытым** пробегом той же скважины: его
   монтаж ≥ остановки последнего закрытого (с допуском на смену в несколько дней).
   Нарушения в первой сборке: §8.4.
7. **Фильтр не-нефтяных стволов из `svod_build_wellidentity_prompt.md`** — в первой
   сборке рассольных (`рс`) строк 0, это правильно; сохранить.

## 5. Колонка «Флаг отказа» — контракт с потребителем

Первая сборка ввела «Флаг отказа» (старый «Failure Flag» удалён; «Признак отказа» — это
ТЕКСТОВАЯ подклассификация Преждевременный/Многосуточный/…, НЕ флаг — не переименовывать
и не переиспользовать). Наблюдаемая семантика, которую потребитель теперь считает
контрактом:

* **1** = настоящий отказ (1657 строк);
* **0** = подъём не-отказ (ГТМ 1103, ППР 29, …) И все открытые пробеги (550);
* **−1** = неразрешённый исход (85 строк, в основном «Прочие») — **потребитель полностью
  ИСКЛЮЧАЕТ их из анализа** (решение пользователя 2026-07-22). Лучше довести их до 0/1;
  пока −1 существует — он должен означать ровно «исход неизвестен».

## 6. Инварианты, которые нельзя сломать

* **Закрытые пробеги не трогаем** — добавление живых не меняет историю отказов.
* **Одна скважина — максимум один живой пробег.**
* **Событие живого пробега = 0 (цензура)**, «Флаг отказа» = 0.
* **Наработка живого пробега ≤ календарь с монтажа** (в ПДК уже встречались ННО >
  календаря на 362 сут; в текущей сборке 50 ЗАКРЫТЫХ строк с Наработка > календарь+30 —
  §8.3).

## 7. Тесты

* **R1 — открытые пробеги есть**: строк с пустой «Дата остановки» ≈ числу работающих
  насосов по техрежиму. *(Первая сборка: 550 — ПРОЙДЕН.)*
* **R2 — покрытие живого парка**: каждый работающий по техрежиму насос имеет открытый
  пробег. *(Первая сборка: 8 нефтяных скважин, которые Big считает работающими, открытой
  строки не имеют — §8.5.)*
* **R3 — монотонность**: монтаж живого пробега ≥ остановки последнего закрытого той же
  скважины (допуск ~7 сут). *(Первая сборка: 2 нарушения — VT_5101, YA_292, §8.4.)*
* **R4 — наработка ≤ календарь** для всех строк, не только живых. *(Сейчас 50 нарушений
  на закрытых.)*
* **R5 — наработка живых заполнена и согласована с техрежимом**: не пустая (сейчас
  пустая у всех 550) и |Наработка − ННО_техрежим| в допуске; систематический сдвиг
  (~49 сут) — объяснить и задокументировать.
* **R6 — живые не создают отказов**: сумма строк «Флаг отказа»=1 не меняется от
  добавления живых.
* **R7 — не-нефтяные исключены**: `рс`-строк 0. *(Первая сборка: ПРОЙДЕН.)*
* **R8 — нет дат из будущего**: монтаж/остановка/демонтаж ≤ даты сборки. *(Первая
  сборка: Vt_7805 с демонтажом 2026-11-04 — §8.3.)*
* **R9 — порядок дат внутри строки**: монтаж ≤ остановка ≤ демонтаж. *(Сейчас 7 строк
  остановка < монтаж и 41 строка демонтаж < остановка.)*

## 8. Разбор ПЕРВОЙ сборки (файл от 2026-07-22, 3424 строки)

### 8.1 Что получилось

550 открытых пробегов; живой парк потребителя теперь 548/548 из Свода (было 12/573);
ГТМ/ППР корректно получили «Флаг отказа»=0 (раньше 453 ГТМ-строки были помечены отказом);
рассольных строк нет. Это главный результат — механизм работает.

### 8.2 Наработка открытых строк ПУСТАЯ (0 из 550)

Требование §4.3 не выполнено. Временное решение потребителя: возраст живого насоса =
календарь на **30.06.2026** (`config.SVOD_OPEN_ASOF`, решение пользователя). Это
календарные сутки, а не ННО — с известным сдвигом ~49 сут. Заполнить техрежимной ННО и
записать дату среза в файл (§4.4).

### 8.3 Грязные даты

* **Vt_7805**: демонтаж 2026-11-04 при остановке 2026-04-14 — дата из будущего;
  потребитель исключает такие строки (граница `config.SVOD_FUTURE_BOUND` = 2026-08-15).
* **7 строк** остановка < монтаж (потребитель исключает), **41 строка** демонтаж <
  остановки и **50 строк** Наработка > календарь+30 (потребитель пока ОСТАВЛЯЕТ — они
  несут валидные отказы; чинить надо в сборке). Длинный разрыв демонтаж−остановка сам по
  себе НОРМАЛЕН (258 строк > 90 сут — скважина ждёт бригаду), фильтровать по нему нельзя.

### 8.4 Открытый пробег, пересекающийся с закрытым (2 случая)

* **VT_5101**: открытая строка с монтажом 2026-02-21 при ЗАКРЫТОМ пробеге
  2026-02-20 → 2026-04-13 (подъём). Скважина одновременно «работает с февраля» и
  «поднята в апреле».
* **YA_292**: открытая 2026-02-11 при закрытом 2026-02-14 → 2026-06-09.

Похоже на дубль одного пробега из разных источников (техрежимная строка против
ПДК-строки) с расхождением дат в 1–3 дня. Потребитель отбрасывает такой открытый пробег
(guard: живой пробег, противоречащий более позднему монтажу или подъёму, — устаревшая
запись), но чинить надо в сборке: дедуп по (скважина, монтаж ± допуск) МЕЖДУ источниками
и тест R3.

### 8.5 Восемь скважин без открытой строки (проверка R2)

Big считает работающими, Свод открытой строки не имеет: VT_3305, VT_3306, VT_2506,
YA_160, YA_173, YA_785, AZ_470, AZ_482. Потребитель их ИСКЛЮЧИЛ из анализа (решение
пользователя — открытые строки Big больше не подмешиваются). Вероятные причины:
YA_785 смонтирован 2026-06-02 — позже среза техрежима; YA_173 «работает» с 2016-09 —
скорее устаревшая строка Big, но проверить по техрежиму. Следующая сборка должна либо
дать этим скважинам открытые строки, либо подтвердить, что они не работают.

## 9. Чего НЕ делать

* НЕ ставить фиктивный подъём живому пробегу (сломает cause-specific оценку).
* НЕ брать наработку живого из приложенческого `сводпрогн3.xlsx` — там «Факт ННО» это
  производная CatBoost-величина (97.7% кратны 1/7), а не сутки.
* НЕ добирать живых из Big — потребитель эту подмешку уже ВЫКЛЮЧИЛ; Свод обязан быть
  полным сам.
* НЕ применять когортных фильтров (например «монтажи 2024+») на этапе сборки Свода — это
  правило ПОДГОНКИ конкретного месторождения, а не свойство реестра.
* НЕ переиспользовать колонку «Признак отказа» под флаг — потребитель читает «Флаг
  отказа», а «Признак отказа» остаётся текстовой подклассификацией.
